# MCP for agents

Core includes a [Model Context Protocol](https://modelcontextprotocol.io) (MCP) server. Any MCP host, such as Claude Desktop, Claude Code, Codex, Cursor, or a Home Assistant agent, can connect to it and read or control the Pod in plain language. "How did I sleep?", "Set my side to 68 for an hour", and "Is everything OK?" each map to one tool call.

## Connect a host

The endpoint is a stateless Streamable HTTP server on the same port as the web app. Replace `POD_IP` with your Pod's address or `sleepypod.local`.

```text
http://POD_IP:3000/api/mcp
```

<Tabs items={['Claude Code', 'Claude Desktop', 'Codex', 'Cursor', 'Other hosts']}>
  <Tabs.Tab>
    ```bash
    claude mcp add --transport http sleepypod http://POD_IP:3000/api/mcp
    ```

    Run `claude mcp list` to confirm the server is connected, then ask Claude Code about the Pod.

  </Tabs.Tab>
  <Tabs.Tab>
    1. Open **Settings → Connectors** (or **Integrations** on older builds).
    2. Choose **Add custom connector**.
    3. Name it `sleepypod` and paste `http://POD_IP:3000/api/mcp` as the URL. Leave authentication empty.
    4. Enable the connector in a chat from the tools menu.
  </Tabs.Tab>
  <Tabs.Tab>
    ```bash
    codex mcp add sleepypod --url http://POD_IP:3000/api/mcp
    ```

    This writes an `mcp_servers.sleepypod` entry to `~/.codex/config.toml`. Run `codex mcp list` to confirm.

  </Tabs.Tab>
  <Tabs.Tab>
    Add the server to `.cursor/mcp.json` in your project, or `~/.cursor/mcp.json` for every project:

    ```json
    {
      "mcpServers": {
        "sleepypod": {
          "url": "http://POD_IP:3000/api/mcp"
        }
      }
    }
    ```

    Cursor shows the server under **Settings → MCP**; enable it there if it is listed as disabled.

  </Tabs.Tab>
  <Tabs.Tab>
    Any host that supports remote MCP servers over Streamable HTTP can connect. Register a server of that type with the URL above and no credentials. Hosts that only support stdio servers can use a bridge such as `mcp-remote`:

    ```bash
    npx mcp-remote http://POD_IP:3000/api/mcp
    ```

  </Tabs.Tab>
</Tabs>

**There is no authentication.** Like the [REST API](/developers/api/), the MCP endpoint trusts the local network. Do not port-forward it or expose it through a public reverse proxy. Browsers cannot reach it cross-origin: a request with an `Origin` header that does not match the Pod's host is rejected, which blocks DNS-rebinding pages.

## What the assistant can do

The server is intent-shaped, not endpoint-shaped. Each tool describes something a person would ask for, using the shared Core procedures. Every tool calls the same procedures the web app uses, so validation, side locks, the pump-stall guard, and live updates all apply.

| You say                                                         | Tool                  |
| --------------------------------------------------------------- | --------------------- |
| "What's the bed set to?" / "Is it priming?"                     | `get_pod_status`      |
| "Who's in bed?"                                                 | `get_bed_occupancy`   |
| "How warm is the room?"                                         | `get_environment`     |
| "How did I sleep?" / "How much deep sleep?"                     | `get_sleep_summary`   |
| "Bedtime this week?"                                            | `get_sleep_history`   |
| "Is my HRV trending down?"                                      | `get_vitals_trend`    |
| "Set my side to 68" / "Warm it up for an hour"                  | `set_temperature`     |
| "Turn my side off"                                              | `set_power`           |
| "Go back to the schedule"                                       | `resume_schedule`     |
| "68 now, 72 at 3 am, wake at 7" (tonight only)                  | `run_once_curve`      |
| "Buzz my side" / "Snooze 10 minutes"                            | `manage_alarm`        |
| "Prime the pod"                                                 | `prime_pod`           |
| "What's my schedule?"                                           | `get_schedules`       |
| "Every weekday cool to 66 at 10 pm" / "Delete Monday's alarm"   | `manage_schedule`     |
| "What unit is it on?"                                           | `get_settings`        |
| "I'm away until Friday" / "Rename my side"                      | `set_side_settings`   |
| "Switch to Celsius" / "Dim the LED at night"                    | `set_device_settings` |
| "What's controlling the bed tonight?"                           | `get_automations`     |
| "Pause all automations" / "Make a rule that cools when HR > 60" | `manage_automation`   |
| "Something's wrong" / "Is the bed actually cooling?"            | `diagnose_pod`        |
| "Show me the logs"                                              | `get_logs`            |
| "Clear the pump alert" / "Restart the piezo service" / "Update" | `pod_maintenance`     |

Temperatures accept your unit (`F` or `C`, defaulting to the device setting) and are converted to the 55–110°F hardware setpoint. Errors come back as readable text with the Core error code, so the assistant can explain "pump stall guard tripped" instead of retrying.

## Sleep-stage rules

| Request                                                                | Tool                        |
| ---------------------------------------------------------------------- | --------------------------- |
| Inspect saved rules, recent changes, and Watch reference coverage      | `get_sleep_stage_rules`     |
| Compare a preset or edited rules with recent nights without saving     | `preview_sleep_stage_rules` |
| Save a reviewed candidate or reset to defaults                         | `set_sleep_stage_rules`     |
| Import extracted Watch heart-rate samples or stage segments for a side | `import_apple_watch_data`   |

Preview accepts a preset, a complete ruleset, or indexed condition overrides, for up to 14 nights. Compare reference coverage, stage minutes, Cohen’s kappa, and per-stage recall. Missing Watch overlap cannot establish agreement.

To apply exactly what was previewed, pass the returned `candidateRuleset` as `ruleset` to the save tool. Overrides are resolved again against the saved rules at save time. On `CONFLICT`, inspect the current rules before retrying. Saving requests a change; processor adoption is a separate state. See [Sleep stages](/core/settings/sleep-stages/) for the UI and video.

Watch import accepts up to 2,000 records per array, with Unix-second timestamps and an explicit side. Repeated records are skipped. Check `stageError` for partial success. For a full Health export, use [Upload Apple Watch data](/core/biometrics/#explore-vitals-and-import-watch-data) instead of putting the archive in model context.

## Biometric calibration

| Tool                            | Purpose                                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------------ |
| `inspect_biometric_calibration` | Inspect metric definitions, profiles, runtime state, references, sessions, and replay admission. |
| `import_biometric_reference`    | Preview normalized reference records, then commit with the exact preview hash.                   |
| `propose_biometric_profile`     | Save an immutable candidate without activating it.                                               |
| `manage_biometric_experiment`   | Freeze datasets, retain selected waveform sources, and manage experiments with pinned protocols. |
| `backtest_biometrics`           | Queue, inspect, list, or cancel replay jobs; read reports and bounded trace pages.               |
| `apply_biometric_profile`       | Request explicitly authorized validated or manual activation, reset, or rollback.                |
| `release_biometric_artifacts`   | Delete references or release datasets and reports; report release requires its content hash.     |

A candidate is not an active profile, and a replay is not proof of processor adoption. Validated activation pins the evaluation and report identity and requires matching qualification policies and evidence. Manual activation requires explicit acknowledgment that the revision is unvalidated. See [Biometric calibration](/core/settings/biometric-calibration/) for review and recovery.

Reports return compact summaries with omitted-detail indicators and a local REST path. Trace requests use the exact report hash and return at most 500 original intervals per page. Report resources are available at `sleepypod://biometrics/reports/{id}`; discover IDs through the backtest list. Released reports remain unavailable.

Processing stays on the Pod, but a connected MCP host may send returned data to its model provider. These tools do not authorize off-pod waveform transfer or executable algorithm installation.

## Saved curves

`get_saved_curves` lists templates. `manage_saved_curve` saves or deletes one; saving the same name replaces that template. Templates have no assigned side or days and do not run by themselves.

`apply_sleep_curve` accepts points or a saved `curveName`, a side, and days. Start with `mode: "preview"` to inspect replaced rows, preserved alarms, warnings, and the final temperature action. `mode: "apply"` with the reviewed arguments writes the curve. Optional notes replace the selected days’ previous notes. See [Saved curves and notes](/core/schedules/#saved-curves-and-notes).

## Resources and prompts

`sleepypod://status` and `sleepypod://settings` provide compact device context. `sleepypod://biometrics/algorithms` describes metric definitions, while `sleepypod://biometrics/profiles/left` and `sleepypod://biometrics/profiles/right` report profile and runtime state.

The built-in prompts are `morning_report`, `bedtime`, `design_sleep_curve`, `calibrate_biometrics`, `explain_biometric_difference`, and `develop_biometric_algorithm`. They guide host workflows; they do not bypass server validation or grant permission to apply changes. The algorithm-development prompt adds no execution or installation tool.

## Approvals and safety

Tool annotations tell the host which calls are read-only and which change or delete something. Reads such as `get_pod_status` and `get_sleep_summary` are marked read-only. Anything that deletes, restarts, re-energizes, or replaces an active curve is marked destructive, so a well-behaved host asks before running it. The server's own instructions also tell the model to confirm before priming, maintenance actions, and schedule deletion.

Temperature precedence is the same as everywhere else in Core, highest first: manual hold, run-once curve, automation, schedule. See [Temperature and power](/core/temperature/).

Tool output is untrusted input for the model. Logs, sleep records, and settings can contain text written by anything on the LAN or by firmware. Annotations are hints to the host, not a security boundary.

## Deliberately not exposed

Developer and installer surfaces stay REST-only: raw hardware opcodes, raw sensor files, database row browsing, sensor calibration triggers, MQTT, HomeKit, and archive-push configuration, automation backtests, cap-zone replays, and canonical vitals ingestion. They are either dangerous without context or useless to a sleeper. Use the [API reference](/developers/api/) for those.
